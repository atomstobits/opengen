# Trusted generation attribution and key rotation

This feature module is a source candidate. It requires the reviewed C5 migration and integrator-owned admission/auth hooks before its behavior is available through HTTP, compatibility, browser or MCP endpoints. No live provider or hosted client verification is implied.

Only authentication code constructs `GovernancePrincipal`. API/browser projections preserve key ID, key kind, membership ID and `keySecretVersion`. OAuth projections additionally preserve `grantId`, `clientId`, `oauthResource` and the stable source API key when the grant is key-derived. A membership-derived grant has no fabricated source key. Refresh keeps the grant/source IDs; rotation keeps the key ID. Authentication projects access-token `authorityExpiresAt`, which is rechecked after preparation separately from longer-lived key/grant expiry. Verified external JWTs explicitly set `externalOAuth: true`, their expiry and the verified member identity; they do not invent a native grant/client/source key. Native grants missing their identifying tuple fail closed.

Call `revalidateGovernanceAuthority(client, principal)` inside the final workspace-reservation transaction, after input preparation. It locks workspace before key/grant/member rows, rechecks active authority and narrows authenticated permissions against current key/grant policy. Use the returned principal to constrain the prepared request and choose **every** primary/fallback route again. A policy narrowed during preparation must reject incompatible prepared input; input preparation never authorizes spending. The transaction helper uses only its caller's `PoolClient`, so pool size one needs no nested checkout. No provider or network calls belong in this transaction.

Sourced grants follow source-key revocation/expiry/policy and source membership removal, including future schemas that record both membership and source key. Member grants follow the original accepted-membership epoch. Reinvitation cannot revive old authority. Archived bound policies deny new use. Authentication must project the newly read key version: a missing or stale version cannot admit direct API/browser calls. Token refresh authentication uses the same current source-key/grant checks.

`attributionForPrincipal` produces a private admission snapshot with key/member/grant/client IDs. Read-only history uses that snapshot, never today's current member/key, and legacy null attribution remains unknown. Project/tags use `parseGenerationMetadata`: optional project (80 characters), at most 16 tags, ASCII tag keys (64 characters) and values (160 characters), no control characters or whitespace padding. Unknown fields, including actor IDs, fail validation. Metadata is stored outside model input, participates in immutable request/idempotency hashing, and is never forwarded upstream by default or published.

An unrestricted active administrator with `keys:write` can call `rotateKeySecretInTransaction(client, actor, keyId, expectedSecretVersion)`. A monthly-capped key cannot change governance or mint an uncapped replacement even when it carries an administrative scope. Use the unrestricted signed-in workspace administrator for governance. The caller owns commit/rollback and returns the token only **after commit** with `Cache-Control: no-store`. The stable key row receives a hashed new secret/version; the old hash stops working, sourced browser sessions are deleted and sourced OAuth grants are revoked atomically. Other membership grants are independent. Monthly cap usage stays on the same key ID. Old jobs and attribution do not change. A failed transaction preserves the old secret and grant authority.

Rotation requires the last observed secret version. A replay at the old version gets `409 key_rotation_conflict`; it never rotates a second time. If the response is lost, refresh key metadata and explicitly rotate a replacement at its current version. Do not automatically retry a rotation or log the token. Key list metadata may expose version/rotation timestamp, never token/hash. Revoking, expiring and archiving authority prevents future admissions while accepted jobs retain their frozen policy and continue recovery/settlement.

Shared hook obligations: preserve all new principal fields in MCP authority projection (the baseline drops them); populate key version in both direct-key and browser-session reads; pass principal through native/compatibility/MCP submit; revalidate at final reservation; validate/store metadata separately; use the returned narrowed policy in re-quote/fallback selection. Governance mutations must use workspace-first locking. OAuth exchange/refresh/revoke paths that mutate authority must share workspace-first ordering before row locks, including refresh/code rows, to avoid lock-order inversions with rotation.
