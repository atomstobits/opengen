# Local billing integration through migration 025

The shared core integrates the verified billing domain checkpoint on the recovery branch after PR 5. Migration 023 installs explicit funding authority, recharge policy and audit. Migration 024 adds the processor registry, customer and setup records, mandates and private documents. Migration 025 adds recharge state, shared PaymentIntent ownership and funding risk links. The populated upgrade retains historical orders, events, holds, wallet entries, pending generations and credential scopes.

The general key and OAuth scope vocabulary is preserved. The billing bridge derives its separate capabilities from a current funding-owner approval or a delegation to an exact API key or native OAuth grant. The bridge reloads source and approval versions in the transaction that reads or changes funding state. Human setup uses the approved owner's browser session. Signed setup completion reconstructs the original authority from its locked persisted setup row and checks the current owner, membership epoch, consent and processor binding.

The fixture runtime uses the existing raw-byte webhook route and the shared ledger credit primitive. Its dispatcher resolves the environment and PaymentIntent to one manual or automatic funding owner. Manual credit uses the bound Checkout, and automatic credit uses the authoritative paid PaymentIntent. The same owner and credit reference survive event replay. An unmatched observation stays pending, and an early refund follows the bound payment into the existing spending hold queue. The normal worker turn accepts the injected fixture runtime and can retrieve a known payment when the automatic charge gate is off.

The billing page checks current browser workspace and recovery scope before showing scoped controls. Native and MCP discovery expose four policy and history operations when the fixture runtime is mounted, with separate scope and financial-effect metadata. Human setup, portal, delegated authority changes, payment authentication and operator actions use their specific HTTP authorization.

The fixture runtime requires explicit construction and test-mode transports. Environment-driven startup uses legacy manual billing. The source checkpoint retains the fixture pricing assumptions and commercial choices in [the billing decisions](../BILLING-DECISIONS.md). Activation requires approved owner enrollment, reviewed fee and funding terms, qualified cost producers, a verified Stripe account and signing configuration, and the separate sandbox and deployment rehearsal. The deployment rehearsal must fence older payment writers before scoped funding starts.
