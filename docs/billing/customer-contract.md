# Customer, mandate and document lifecycle — B3

2026-11-05, fixture implementation. The integration owner assigns the forward migration from [customer-schema.sql](customer-schema.sql). These modules are additive source, not hosted activation or completed Stripe sandbox evidence. They do not change the existing payment order serializer, balance or ledger.

## Contracts and ownership

`packages/engine/src/billing-customer.ts` exports `BillingCustomerStore`, `CustomerTransport`, `CustomerActor` (the complete `BillingPrincipal` source tuple), `VerifiedSetupEvent`, `BillingDocument`, `RechargeAttemptRequest`, `RechargePayment` and `RechargeTransport`. `apps/server/src/billing-stripe.ts` exports the injected `StripeBillingTransport` and the additive `ManualInvoiceOrderV2` serializer. No new dependency or SDK upgrade is required: use the existing Stripe 23.1.0 instance pinned to API `2026-10-28.endive`.

Construct the store with the existing pool, required `BillingProcessorEnvironment` (`id`, `accountId`, `livemode`), server-owned immutable terms `{version,text}`, B2's `authorizeInTransaction` callback and the existing PaymentStore's `lockExternalInTransaction` and `admitExternalInTransaction` callbacks. `allowPortal` defaults to false. The transport receives the existing configured Stripe instance and `{enabled,processorEnvironment,publicUrl,portalConfigurationId?}`.

The integration owner registers the server-controlled environment with `registerBillingProcessorEnvironmentInTransaction` before writing owner or customer records. The registry rejects changes to a registered account or mode and permits one logical ID per verified account and mode. The current Stripe account check cannot distinguish aliases for the same account and mode. Separate sandbox namespaces therefore require distinct verified account IDs. Customer, setup, mandate, document and setup-event rows record the environment ID, account ID and mode with composite foreign keys. Key rotation uses the existing environment ID with a newly verified SDK instance, preserving local request and external idempotency identities.

An explicit server workflow admits one account read and calls `await transport.verifyProcessorEnvironment(assertTrustedContext)`. The injected callback verifies the configured namespace and key mode, then the adapter retrieves its own account and compares the returned account ID. The Stripe Account response does not carry a `livemode` value. The adapter keeps the result in memory and requires it before billing I/O. The store also checks that the transport proof matches its registered environment. Ordinary history and policy reads perform no account verification requests. `verifiedLegacyCheckoutTransport()` binds the existing Checkout serializer to this same SDK instance and proof. Constructing the wrapper performs no external request. Each wrapper operation checks proof before calling Stripe. The verifier and account-read admission remain part of shared activation wiring. [Stripe account retrieval](https://docs.stripe.com/api/accounts/retrieve)

```ts
const customers = new BillingCustomerStore(engine.pool, {
  processorEnvironment: reviewedProcessorEnvironment,
  terms: reviewedTerms,
  authorize: policy.authorizeInTransaction.bind(policy),
  lockExternalInTransaction: payments.lockExternalInTransaction.bind(payments),
  admitExternalInTransaction: payments.admitExternalInTransaction.bind(payments),
  allowPortal: false,
});
const transport = new StripeBillingTransport(configuredStripe, {
  enabled: false,
  processorEnvironment: reviewedProcessorEnvironment,
  publicUrl: 'https://opengen.dev',
});
```

Actual browser provenance, fresh session/recovery/workspace binding and Origin checks belong in the HTTP adapter before supplying an actor. A caller's `consent:true`, administrator role, API-key-backed cookie or request-supplied actor is insufficient. B2 must require the explicit approved funding-owner/envelope row and current source key/grant/membership; merely extending scope defaults must confer no new authority. Portal capability and the initial funding-owner establishment remain Section11 decisions.

## Persistent customer and setup

`ensureCustomer(actor,workspaceId,transport)` requires the current approved human administrator. One local row per workspace/environment is persisted and committed before Customer creation. The stable `opengen-customer-v1-<uuid>` key survives lost responses. The persisted `customer_v1` serializer and `2026-10-28.endive` API version are sent on every POST; unsupported versions fail before dispatch. A lease rejects concurrent dispatch; after twenty hours an unresolved request requires review and cannot create another customer. No arbitrary Customer ID is accepted from the caller or bound through Stripe metadata. Create response identity/environment are checked, then its opaque ID is retained even if the initiating source is later revoked; retention does not activate a mandate.

`startSetup(actor,workspaceId,{idempotencyKey,consent,termsVersion},transport)` requires explicit consent to the exact server-owned terms version and current B2 human-owner proof. The terms text must describe authorized payments, amount determination and frequency. The local setup stores its terms snapshot, original source tuple, human membership, consent reference, fixed expiry and stable request key before external I/O. The setup freezes serializer `setup_checkout_v1` and API version in its local row. One unfinished setup exists per workspace/environment. Retries reuse the same shape/key and original terms even when a deployment changes the terms offered for new setups; ambiguous setup older than twenty hours requires review. A user cancel or browser return does not activate anything.

Hosted Checkout uses `mode:setup`, `currency:usd`, the stored Customer and documented dynamic payment-method defaults. The generated SetupIntent's documented `usage` default is `off_session`; Checkout's API does **not** accept `setup_intent_data.usage`. Reconciliation requires the retrieved SetupIntent's actual usage to be `off_session`, status `succeeded`, and its retrieved payment method to belong to the same Customer/environment. No raw payment-method fields, client secrets or card details are persisted.

`reconcileSetup(event,transport)` receives the exact-raw-byte verified event with `processorEnvironment` supplied by the trusted endpoint context. The environment comes from server configuration outside the Stripe payload. Dispatch `checkout.session.completed`, `checkout.session.expired` and `payment_method.detached` here in addition to the existing manual-payment handlers. Before any activation it retrieves the already-bound Checkout Session, SetupIntent and PaymentMethod and matches the stored session/customer/environment/client reference and signed event fields. An unbound session returns retryable `setup_unmatched`; recover the original create request by its stable key rather than bind metadata or create a replacement. Duplicate completion is journaled once. Reads/return URLs do not run this function.

The final transaction rechecks the original full source tuple, explicit owner proof, accepted administrator membership and customer binding. Setup and mandate freeze the owner authority version, consent reference and accepted-membership epoch; even reapproval of the same human with a new envelope cannot validate the old setup. Stale approval commits a visible setup review state and returns `setup_authority_revoked` without activation. Revoked/expired source or removed funding owner cannot activate an old page's mandate. This conservative case remains visible for approved human recovery/operator handling; no replacement charge or automatic reauthorization is attempted. Successful replacement revokes the former local mandate; old completion events cannot restore it. Signed method detachments are journaled before ownership is available and revoke matching active local mandates. Completion freshly retrieves the PaymentMethod, then uses an environment/method advisory barrier before workspace locking and refuses activation if the detachment journal exists. A detachment arriving after an earlier attached-method read therefore cannot create a valid mandate. Journal ownership binds only through the verified SetupIntent/session or an existing owned mandate, never metadata. Historical detachments require explicit review rather than silently enabling the method after reattachment. Explicit `revokeMandate` requires current approved human-owner authority; delegated policy managers can disable policy without changing the mandate itself. New worker attempts must also retrieve/validate the current method and recheck owner/mandate/policy under B4's admission contract; an accepted external charge still reconciles after revocation.

## Private portal and documents

`portal` requires B2 management authority, explicit `allowPortal:true`, the owned stored Customer/environment and a reviewed portal configuration. The store retrieves Customer identity before creating a short-lived portal session, validates returned customer and `billing.stripe.com` URL, and fixes the return origin. Subscription/tax/payment-management portal settings must be reviewed independently. A portal method change does not silently choose a new recharge method or create fresh mandate consent.

`documents` is a cached database read requiring `billing:read`; it performs no Stripe I/O and returns a bounded cursor page with optional invoice/receipt filter. It excludes Customer IDs, environment internals, raw Stripe payloads and generation content. Cursor ownership is checked. `syncDocuments` is an explicit authenticated mutation requiring billing read authority, a bounded upstream page and shared external request admission; expose it as POST, not as an automatic GET side effect. Each returned document must match the stored Customer/environment and its receipt/invoice kind. Safe HTTPS Stripe-hosted links only are retained. Wallet entries, charge receipts and invoices remain separate; neither invoice nor document sync grants credit.

`createManualInvoiceSession` requires a newly persisted `requestVersion:'customer_invoice_v2'`, processor environment and owned customer reference. It adds `customer` and `invoice_creation:{enabled:true}` while keeping USD face value, dynamic methods, fixed return URLs and no tax/promotions/automatic conversion. The integration owner must allocate and freeze a **new** serializer/version on **new orders** before using it. It must not feed this method an old uncertain order or reuse an old Stripe idempotency key with changed parameters. The existing legacy `StripeCheckoutTransport.createSession` remains byte/parameter compatible. Customer billing documents are not a conclusion about tax compliance.

## Off-session transport for B4

`RechargeTransport.createRecharge({requestVersion:'recharge_pi_v1',apiVersion:'2026-10-28.endive',processorEnvironment,id,customerId,paymentMethodId,amountCents,stripeIdempotencyKey})` refuses unsupported persisted versions before external I/O, pins the per-request API version and uses explicit `confirm:true`, `off_session:true`, USD amount and the persisted method/customer. `retrieveRecharge(id)` recovers the same PaymentIntent. Both return only `id,customer,payment_method,currency,amount,amount_received,status,livemode` plus the optional safe `authentication_required` boolean. This flag is derived from actual Stripe state/error evidence and never replaces Stripe status. An off-session `requires_payment_method` with an `authentication_required` error remains in-flight authentication work, rather than being mistaken for an ordinary decline that admits another charge. Authentication-required/decline errors with an authoritative intent preserve that ID/state while excluding client secrets; uncertainty without an authoritative object returns a sanitized retryable error. The caller must validate **every** returned identity/amount/environment against its stored attempt before any credit. Metadata never supplies authority. Transport calls alone cannot reserve or credit the ledger.

`RechargeRecoveryTransport.retrieveRechargeRecovery(originalPaymentIntentId)` performs a read-only, version-pinned GET with `expand:payment_method`. It supports an original `requires_action` intent, or `requires_payment_method` with verified `last_payment_error.code:authentication_required`, with an expanded, owned card method and the same environment. It validates the secret prefix against that exact intent and returns `{payment,clientSecret,methodType:card}` only for the separate approved human-owner recovery action. The server must first validate original attempt, amount/currency, policy/owner and request/recovery binding, consume shared request admission, and use `Cache-Control:no-store`. The client keeps the returned secret only in memory and uses official Stripe.js `confirmCardPayment(secret)` with the attached method; it must not create a replacement PaymentIntent. No new PI is created by this transport. The ordinary payment projection, persistence and audit never contain this secret. Unsupported, missing, detached or unexpanded methods fail closed.
