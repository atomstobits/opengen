## Continue and verified callback

A signed HttpOnly `og_login_intent` holds a ten-minute intent ID, server policy snapshot and optional pending MCP request. The hidden action token is separately signed with its purpose, intent ID and expiry. POST `/auth/login` accepts only an exact public Origin and a UTF-8 URL-encoded form no larger than 2 KiB, with one fixed action and one token; missing Origin, duplicate/unknown fields and stale/mixed/tampered intents are refused. Neither a Referer nor a caller-supplied policy/return URL establishes authority. The notice uses `Referrer-Policy: same-origin`: a `no-referrer` navigation form would send `Origin: null` and fail the required exact-origin check. Cross-site referrers remain withheld, and callback/error responses use `no-referrer`. This follows the [Fetch Origin-header algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header). The raw-form parser is encapsulated to these login routes and does not change OAuth token/revoke parsing.

After validated Continue, a small script-free navigation document performs the cross-origin IdP handoff; a direct form redirect chain would be blocked by `form-action 'self'` in some browsers. The form restriction stays unchanged, and only the verified discovery endpoint supplies the HTTPS navigation target. The existing signed OIDC transaction includes that same intent alongside PKCE verifier, state and nonce. The callback relies on openid-client's verified code/ID-token exchange, validates the intent before and after asynchronous work and checks the pending MCP request before returning to consent. A later raw cookie cannot change the chosen return. Legacy transactions lacking Continue evidence must restart sign-in. Invalid/expired sign-in clears only its intent/OIDC/pending-MCP cookies so a stale request does not trap direct entry; it never clears the existing session used for accepted-job recovery. Unknown provider/store errors are redacted at the public callback boundary. Existing accepted-job access/recovery, API-key/OAuth authentication and scopes remain unchanged.

## Minimal immutable receipt

Only the adopted/effective-policy branch calls `TermsReceiptStore.recordVerifiedAcceptance`, after verified issuer/subject and validated Continue, before issuing a browser session. The default draft branch never writes a receipt. The writer is internal: there is no customer receipt-write endpoint or generation/funding acceptance field, and generic `identity()` and invitation `accepted_at` retain their original meanings.

Migration 029 adds `mr_terms_receipts` with exact issuer/subject, server-selected policy version/digest, fixed `human-terms-continue-v1` notice, `continue` action, `oidc-verified` method and database timestamp. It adds no separate email, IP, device, token, prompt or workspace fields beyond the verified issuer/subject and stated evidence. Keys bind exact issuer/subject strings; matching emails never link identities. Same identity/version/digest retries return the first record without an UPDATE. A different digest for an already recorded identity/version is a conflict. Ordinary database operations are protected by triggers refusing UPDATE, DELETE and TRUNCATE, including empty statements. Existing migrations 001–028 remain unchanged.

The receipt evidences a verified human identity and validated identified-policy Continue. It does not guarantee that the final session cookie reached the browser. If later session creation or the last pending-request check fails, the already valid assent receipt can remain; no session cookie is issued from that failure. Failed OIDC verification and invalid/stale intent never reach the writer. Retention/adoption/privacy operations require their own documented operational decisions; this immutable audit table is not an account-deletion API. Before any ACTIVE receipt writing, the operator must approve and qualify the [scoped receipt retention/disposition procedure](TERMS-RECEIPT-DISPOSITION.md), including a receipt-specific plan identifying the purpose and data, access owner, actual retention criteria and preservation/hold process, handling of valid rights requests, and a reviewed disposition/correction procedure compatible with the immutable evidence and recovery copies. Migration029 supplies no expiry scheduler or account-deletion path, so a written period alone does not implement disposition. Do not remove immutability controls as a blind workaround; qualify any narrowly scoped implementation separately before activation.
