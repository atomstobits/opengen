## Offline manifest check

`scripts/core-activation-preflight.mjs` reads only an explicit regular JSON manifest (128 KiB maximum), migration source, the explicit engine migration loader and local Git metadata. It imports the existing pure bootstrap bucket policy; it never invokes bootstrap, deployment, the upgrade harness, cloud commands, a database, an HTTP client or an environment/config loader. It rejects symlink manifest files and does not echo input values, paths or parser/subprocess errors. Supply **sanitized assertions only**, never secrets, signed URLs, customer identifiers/content, credentials or a bootstrap receipt.

From a clean checkout, using Node 22.12 or newer:

```sh
node scripts/core-activation-preflight.mjs --example > /absolute/private/synthetic-activation.json
node scripts/core-activation-preflight.mjs --manifest /absolute/private/synthetic-activation.json
```

The example uses a reserved synthetic origin/digest and copies the first 13 source migration hashes for demonstration. It is not an observation of the deployed database. An operator-sanitized manifest must use independently recorded applied migration names/checksums, exact candidate Git commit/tree, matching immutable API/worker image digests, reviewed bucket policy and runtime retention assertions. Build provenance linking digest to source remains external. Never replace actual applied checksums with example values to make a failure pass.

Exit 0 means `preflight-passed`: assertions are internally compatible with source. Exit 1 means `preflight-blocked`: inspect fixed check codes. Exit 2 means bounded input/source/usage failure. Every result says `hostedReadiness: not-established` and retains external gates, even on synthetic/operator-sanitized success. Dirty/different source, mutated/noncontiguous applied migrations, input age deletion, missing conditional-upload CORS headers, public cache policy, retention drift, changed vault key, mixed old writers or unsafe rollback assertions block the check. Policy comparison intentionally requires the existing exact GCP source policy; an alternative needs a reviewed source change.

`MR_INPUT_RETENTION_MS` maps to both runtime retention fields; JSON `null` means unset. `advertisedInputRetentionMs` must match, including null when no automatic expiry is promised. `vaultKeyVersionUnchanged` asserts preserved key material/version for existing connections and frozen credential snapshots without disclosing the secret reference/value. The cutover object describes required operator actions; this tool does not implement admission maintenance or stop workers.

The current manifest also requires `apiExecutionScope` and `workerExecutionScope` to match an explicit `unrestricted` or `qualification-sg-v1` profile. Record the effective parsed configuration, not a guessed value. `apiQualificationFirstFrameSha256` and `workerQualificationFirstFrameSha256` must match: use JSON `null` when unset, or a normalized lowercase 64-character digest only with `qualification-sg-v1`. The synthetic example leaves both pins null, so it does not imply scoped image-to-video readiness. Real fixture fingerprints remain in the private operator manifest; checker output does not echo them. The pin limits first-frame bytes and is not evidence of provider qualification or permission to spend. Profile activation and preservation of older queued work require separate owner review; the checker does not change jobs or holds.

## Rollback boundary

Before current-core writes, an older image is a rollback candidate only after proving it handles migrated schema safely; additive SQL alone does not prove behavior compatibility. After current-core admissions/receipts/pins/capacity/credential snapshots exist, do not restart the older 13-cohort worker or return generation traffic to it. Prefer paused admissions, fenced workers and a forward-compatible fix while accepted work/costs remain durable. Disabling unavailable native verification must preserve truthful unknown and leave generation/settlement outcomes intact.

Do not down-migrate, drop new tables, rotate away required vault/provider credentials, delete pinned objects, clear unknown holds or restore an old DB over post-checkpoint accepted work. Restore requires owner reconciliation of all later upstream acceptance, receipts and settlements first; otherwise paid work can duplicate. Teardown, secret rotation and destructive recovery require a separate reviewed owner decision.
