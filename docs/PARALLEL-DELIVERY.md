## Customer onboarding delivery

1. Inspect existing human OIDC login, browser sessions, workspace membership, key issuance, MCP consent and CLI PKCE login before adding anything. First sign-in already creates an identity/personal workspace; reuse the issuer/subject identity contract. Never link accounts solely by matching email.
2. Design a friendly sign-in/onboarding journey using treg.to and AlleyBloom as references. Preserve OpenGen's forest/ivory/magenta design and restrained retro details. Ordinary customers never enter installation/operator or provider credentials to sign in. Clearly distinguish available sign-in methods from unconfigured deployment capabilities.
3. Deliver welcome → workspace → create an API key or connect an agent → first generation paths. API keys are displayed once, hashed at rest and scoped to the selected workspace. Preserve current membership and admin boundaries. Browser sessions remain HttpOnly and are not exported as agent tokens.
4. Reuse the hosted MCP authorization server and CLI browser-login helpers supplied in the baseline. Add discoverable hosted/local setup instructions and dedicated agent pages. Keep Agent / CLI / API onboarding prominent while retaining a direct browser-creation path.
5. Build client binding as explicit commands with previewable configuration changes, preservation of unrelated settings, private profile files and least-privilege tokens. Do not put tokens in command arguments, URLs, checked-in files or browser storage. Do not mutate the developer's global client settings during implementation/testing.
6. Maintain a dated support matrix distinguishing protocol fixture tests, actual client/version tests and unverified instructions. Cover ChatGPT, Claude, Claude Code, Cursor, Codex and treg-referenced clients where documented. Do not claim live compatibility without evidence.
7. Verify signed-out, first-use, returning-user, workspace switch, create/revoke key, consent denial and local-login recovery on desktop and phone. Use meaningful integration tests for authorization and configuration writes. Report live IdP/client checks that still require deployment or customer configuration.

Owned files should be new onboarding modules/pages and existing dashboard/key components. Avoid editing core generation files, CLI index/login helpers, server app/authentication modules or transport allowlists while integration is in progress. Describe required hooks in an integration note instead. Shared CSS changes must be narrow and scoped. Payments owns its standalone billing component and routes; leave a clear dashboard slot/link for it.

## Payments delivery

1. Read the Stripe Directory, Stripe best-practices and Stripe documentation skills. Inspect existing creditWorkspace, workspace authorization, transaction helpers and ledger constraints. OpenGen sells its own prepaid service credit; this does not require a marketplace payout system.
2. Use a separate Stripe sandbox for development when configuration is supplied. Implement against signed fixtures and a mock transport first. Keep secret and webhook keys in ignored server-only configuration/Secret Manager, never frontend build variables. Do not create live charges or assume the provider-test budget authorizes customer payment activity.
3. Add migration 012 for bounded USD top-up orders and payment/event state. Migration 011 is reserved for MCP OAuth. Enforce integer cents/microUSD conversions, server-side amount limits, stable workspace-scoped idempotency and fixed success/cancel URLs. The local order must exist before an external Checkout request; retries must reuse the same Stripe idempotency key.
4. Create hosted Checkout Sessions for human-initiated, one-time payments. Do not enable automatic recharge, saved-card charging, automatic tax or subscriptions by default. Select payment methods using documented dynamic defaults. Check current official API/SDK versions rather than guessing.
5. Verify webhook signatures over the exact raw body and fail closed when signing configuration is absent. Validate session identity, currency, mode, paid state and face-value subtotal against the stored order. Metadata is not sufficient authority. Handle delayed success/failure, duplicate and out-of-order events; the success page never grants credit.
6. Credit exactly once in the same database transaction as payment reconciliation. The integration chat owns engine/index.ts: propose a small exported transactional credit primitive that both existing operator credit and the new PaymentStore can reuse; do not duplicate accounting rules or nest independent pool transactions. Preserve pool-size-one operation and native PostgreSQL concurrency.
7. Define refund/dispute handling explicitly. At minimum record the event and a billing hold that blocks new spending until reconciled; do not erase ledger history or fabricate a refund. Coordinate the hold admission check with the integration chat. Accepted provider jobs must continue to settle correctly.
8. Provide a standalone Add credit/history/status component and typed authenticated endpoints. Clearly show pending versus credited payments. User cancellation preserves balance. Payment details remain on Stripe Checkout; OpenGen does not collect card numbers.
9. Test concurrent/duplicate webhooks, wrong signatures/order/currency/amount, cross-workspace access, timeout retries, asynchronous payment completion and ledger atomicity. Document sandbox/live configuration and remaining tax/refund operational decisions truthfully.

Own payments.ts modules, payment tests, migration 012 and standalone billing UI/proxies. Do not edit engine/index.ts, server/app.ts, shared transport allowlists or dashboard/workspace.tsx while those files are owned elsewhere. Supply exact wiring snippets in a short integration note. Coordinate package-lock changes at integration time.

## Release gates shared by all three workstreams

All interfaces use the same canonical generation envelope and model/operation capability schemas. Unknown parameters are rejected before reservation or provider calls. Original provider links and regional deployments remain distinct. No fabricated price/performance/support claims.

The release requires exact-commit typecheck, tests, SQL integration, browser/build checks, secret/history/source scanning, source packaging and self-host install/backup/restore validation. Live provider smoke tests have a separately authorized total ceiling of $50; the separate provider-validation workstream has real access/generation evidence and retained unknown-charge holds. Consult its source-safe report, STATUS and the current shared private budget journal before paid admission; do not reset spending from an older document. Hosted identity, real agent-client compatibility, payment sandbox verification, GCP deployment and the finished Hyperframe hero video require dated evidence from their owners. Open source readiness and a production-ready hosted service are separate claims.
