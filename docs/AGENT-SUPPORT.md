## Protocol evidence is separate

These fixtures use synthetic accounts, callbacks, requests and tokens. They do not consume provider credit or authenticate to a real identity provider.

- `tests/mcp-authorization.test.ts`: unit fixtures for exact HTTPS/literal loopback/explicit-port localhost callback validation, delegated restriction intersection and disabled sign-in when OIDC is absent. Database-dependent fixtures cover paying-workspace consent, redirect/resource/PKCE binding, hashed tokens, replay/rotation, membership removal/re-invitation, fixed-key limits and browser-versus-bearer authority. Database tests are conditional on `TEST_DATABASE_URL`; a skipped test is not passing evidence.
- `tests/cli-login.test.ts`: local loopback state/PKCE, private profile output, serialized refresh, revoke-before-delete, unsafe file permissions and redacted endpoint errors. Browser callbacks are programmatically simulated; this is not a third-party client test.
- `tests/local-bindings.test.ts`: temporary-file preview/apply configuration fixtures, preservation of unrelated settings and safe private-profile metadata. This does not run or certify the target agents. See [local binding guide](LOCAL-AGENTS.md).

Record the exact invocation, commit and pass/skip counts in `ONBOARDING-INTEGRATION.md` after validation. Do not upgrade a row based on metadata discovery, configuration being saved, a green protocol test or the client vendor’s generic MCP claim.

## Account, consent and credential boundaries

First configured browser sign-in creates an issuer/subject identity with a zero-credit personal workspace. Accounts are never linked by email alone. Customers do not supply installation/operator or provider credentials for ordinary sign-in.

Hosted clients use their own OAuth grant and private client-managed token storage. Source CLI browser login uses OpenGen’s existing private profile and PKCE helper. A CLI profile is not copied into native MCP configuration; native client authorization is independent. Browser HttpOnly sessions are never exported as agent tokens. The public `/mcp` URL contains no credential. Configuration examples contain public endpoint/launcher information only.

Consent names the client/callback origin, paying workspace and read/generate permissions. A user can deny consent without granting access. Generation can spend the selected workspace balance subject to existing policy; sign-in itself grants no credit. API integrations get separate expiring keys with least-privilege read/generate defaults, stored once by the customer’s secret manager. Admin scopes remain explicit and server-authorized.

Changing workspace in the website does not silently move a fixed key or an existing agent grant. Revoke the old grant and reconnect with the intended workspace. Website sign-out does not revoke independent agent grants. Source CLI logout attempts revocation before deleting the profile; preserve it and retry if revocation fails.

## How to qualify a client

Before changing “unverified,” record the exact OpenGen commit/deployment, client surface/version/build, OS, date and a private evidence location with credentials redacted. Confirm public TLS/reachability and configured identity-provider login first. Test discovery/registration, exact callback policy, PKCE/resource/scope negotiation, consent denial and approved workspace, read-only denial of generation, grant revocation, expiry/refresh, reconnect and account/workspace isolation. Use read-only catalog and quote actions first; generation requires a separately approved budget and no blind retry after uncertain acceptance.

Do not relax redirect, audience, origin, signature, replay or membership checks to make a client pass. OpenGen accepts exactly registered `http://localhost:<port>/<path>` callbacks with explicit positive ports for native-client compatibility. The hostname must be exactly localhost; subdomains, trailing-dot aliases, encoded hostnames and nonloopback HTTP remain rejected. Port, path and query matching are not relaxed. See [the callback security tradeoff](AUTH.md#native-client-callback-policy). A hosted client’s sandbox is not the customer’s local computer. No installer should run merely because a connector setup is available.
