# OpenAI-style endpoint compatibility

The canonical HTTP/MCP API is the full execution contract. These endpoints adapt a selected image/video subset to that engine; arbitrary OpenAI applications are not drop-in compatible. SDK distribution and framework adapters are deferred. This candidate has synthetic conformance evidence; no live compatibility generation or deployed storage transport is qualified here.

All creation requests require a workspace bearer credential with `generate` scope and a stable `Idempotency-Key` (1–200 characters). Reads require `read`. Workspace policies and exact-model/operation/route validation apply before admission. Use exact IDs from `/v1/models` and `/v1/models/schema`; pin a regional route with `route_id`. A provider credential is never an OpenGen bearer credential.

| Endpoint                                    | Accepted body / response                                                                                       | Explicit boundary                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/images/generations`               | JSON `model`, `prompt`; optional `n:1`, `size`, `response_format`, selected quality/format/background controls | Square sizes `1024x1024`, `2048x2048`, `4096x4096` map to canonical 1K/2K/4K and `1:1`. Default `1024x1024` is a tier request, not a guarantee of exact pixel dimensions. Model/route bounds can reject a size.                                                                                                                                           |
| `POST /v1/images/edits`                     | JSON fields above plus `image:{assetKey}` or ordered `image:[{assetKey},…]` (1–10)                             | Owned ready images only; exact model/route count limits can be lower. Omitted size leaves geometry to the canonical edit schema; it does not force a square crop.                                                                                                                                                                                         |
| Edit multipart                              | `multipart/form-data` text fields, `image` or repeated `image[]` containing JSON `{ "assetKey": "…" }`         | This is a qualified owned-reference extension, not binary OpenAI file upload. Binary parts, external URL references, masks and conversions are rejected. Upload/complete via native assets first. Total multipart text is limited to256KiB and24 parts.                                                                                                   |
| Image response                              | `response_format:"url"` (default) or `"b64_json"`; `created`, `data`, `opengen`                                | One owned output. Base64 reads configured private storage, accepts PNG/JPEG/WebP and at most **8 MiB decoded** (about 10.7 MiB base64). Never fetches a provider or caller URL. Larger results require URL delivery.                                                                                                                                      |
| `POST /v1/videos`                           | Asynchronous JSON `model`, `prompt`, `seconds` (integer or digits string), `size`                              | Text-to-video only. Sizes: `1280x720`, `720x1280`, `1920x1080`, `1080x1920`, `854x480`, `480x854`; converted to landscape/portrait and 720p/1080p/480p tiers. Exact route duration and geometry bounds still apply. No remix, edit, streaming inference or multipart first frame.                                                                         |
| `GET /v1/videos/{id}`                       | Compatibility video state plus native `opengen` metadata                                                       | `completed` requires available owned delivery. A generation success with unavailable output is not completed media.                                                                                                                                                                                                                                       |
| `GET /v1/videos/{id}/content` without Range | Authenticated **303** to a short-lived owned capability                                                        | No gateway download or provider URL proxy. Client follows the capability in a separate request without the OpenGen Authorization header. Do not put capability URLs in public logs or pages.                                                                                                                                                              |
| Video content with `Range`                  | **206** bytes from configured owned storage; `Accept-Ranges: bytes`, exact `Content-Range`/`Content-Length`    | One `bytes=start-end`, `bytes=start-`, or `bytes=-suffix` range; at most a 100 MiB stored MP4. **416** for malformed, multiple or unsatisfiable ranges with `Content-Range: bytes */size`. Matching strong ETag/date If-Range keeps206; mismatch returns complete200. Storage ignoring Range fails closed. Foreign jobs are 404 before any object access. |

All create bodies also accept `billing:"managed"|"byok"`, `route_id`, and integer `max_cost_micros` (micro-USD, nonnegative safe integer). Quality, output format and background values retain canonical meanings and model-specific limits; inspect the effective schema. Unknown fields and unsupported combinations fail instead of being dropped. Count greater than one, masks, stream/previews, arbitrary provider options and automatic image conversion are outside this subset. Use canonical HTTP/MCP for richer supported controls.

`b64_json` is a response representation, independent of the requested output codec; there is no transcoding. A successful upstream generation that cannot fit base64 is still the same charged job. The error response includes the existing job ID and recovery metadata; retrieve that job for URL delivery. Do not submit a second generation to change response representation.

| Condition                                       | Image HTTP / video state                            | Recovery                                                                                                   |
| ----------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Available owned output                          | 200 nonempty image data / `completed`               | Use private data; inspect native job for charge/evidence.                                                  |
| Queued/running or image wait exceeds 25 seconds | 202 / `queued` or `in_progress`                     | Keep job ID, poll native job; ending a wait does not cancel work.                                          |
| Generation succeeded; delivery pending/partial  | 202 / `in_progress`                                 | Recover missing delivery slots on the same job while bounded same-job worker retries run. No regeneration. |
| Failed/expired/unverified delivery              | 409 / `failed`, with independent `opengen.status`   | Inspect same job; operator or native delivery recovery as indicated. Settlement is independent.            |
| Failed/cancelled generation                     | 422 image / `failed`                                | Inspect job and charge; cancellation is not a refund promise.                                              |
| `submission-unknown`                            | 202 / `in_progress`; `requires_reconciliation:true` | Keep reservation and original request/key. Operator reconciles acceptance; never blind paid retry.         |
| Base64 too large / invalid output bytes         | 413 or 409, existing job metadata                   | Retrieve existing job for URL delivery or operator recovery. No new submit.                                |
| Foreign job / insufficient scope                | 404 / 403                                           | Correct workspace/scopes; no storage read.                                                                 |

Compatibility metadata includes `job_id`, native `status`, `delivery_status`, `recovery`, `poll_url`, exact `route_id`/`deployment_id`, `reserved_micros` and nullable `settled_micros`. Provider receipts, raw upstream errors/URLs and connection identities remain internal. A short-lived signed URL is a bearer capability; private access does not promise provider zero retention, immediate revocation or identity-bound bytes. Re-read the owned job to refresh expired issued URLs while retained bytes remain available.

Use the [feature API reference](FEATURE-API-REFERENCE.md) for field/default/scope tables and the quote → cap → stable submit → wait/recover sequence. The [canonical input reference](UNIFIED-GENERATION-API.md) describes media roles. Upload completion is distinct from readiness: do not submit an uploading, failed, expired or foreign asset. Replaying an expired job does not regenerate it.

Synthetic edit request (replace the asset key with a ready upload belonging to your workspace):

```json
{
  "model": "bytedance/seedream-5.0-pro",
  "prompt": "Turn the synthetic paper sculpture blue, preserving its shape.",
  "image": [{ "assetKey": "inputs/WORKSPACE/UPLOAD.png" }],
  "response_format": "url",
  "max_cost_micros": 1000000
}
```

Store that body in `edit.json` and use `curl --fail-with-body "$OPENGEN_API_URL/v1/images/edits" -H "Authorization: Bearer $OPENGEN_TOKEN" -H "Idempotency-Key: $OPENGEN_IDEMPOTENCY_KEY" -H 'Content-Type: application/json' --data-binary @edit.json`. Set the configured API origin explicitly; no SDK install is needed. Submit is billable; obtain a canonical quote and approval for the cap first. The cap covers managed customer debit, not an unqualified guarantee over external BYOK charges.

Existing MCP operations `images.generate`, `videos.create`, `videos.get` and `videos.content` use the same handlers/scopes; create calls require top-level `idempotencyKey`. Content returns structured redirect metadata instead of fetching bytes. `images.edit` is also registered in this source candidate; inspect `/v1/operations` on the installation before use. Binary Range delivery is HTTP-only; do not embed videos into MCP text responses. See the fixture-backed [raw HTTP example](../examples/http-feature-contracts.mjs) for canonical JSON/MCP sequences and same-job recovery.
