# Private member notifications

Notifications are a member-specific view of the existing transactional alert outbox. They do not copy prompts, media or credentials. `alert.triggered` and `alert.resolved` remain separate immutable events. Repeated scans of an unchanged condition produce no new event. Alert rules and webhook settings still require `webhooks:write`; personal notification preferences require an active workspace membership and `read` scope. A fixed key without a membership cannot choose a member ID or read another person's preferences.

The combined server registers these routes. The engine's migration manifest includes `018.sql` for member preferences/read state and `021.sql` for verified recipients, email consent and durable email deliveries. Apply the registered migrations before serving the current runtime; source registration does not establish that a hosted database has been upgraded.

| Method and path                                  | Behavior                                                                                                                                                   |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/notifications?limit=30&unreadOnly=true` | `{items,nextCursor}`; descending `(created_at,id)` cursor, limit 1–100, workspace-bound cursor, no private job content                                     |
| `POST /v1/notifications/{id}/read`               | Empty body; sets this member's `readAt` once, repeated reads retain the original timestamp                                                                 |
| `GET /v1/notifications/preferences`              | `{inApp,eventTypes,email,emailAvailable,recipientVerified,emailRecipient}`                                                                                 |
| `PUT /v1/notifications/preferences`              | `{inApp:boolean,eventTypes:["alert.triggered","alert.resolved"],email?:boolean}`; event types may be empty, omission of `email` preserves existing consent |

Every path derives workspace/member identity from the authenticated principal and rechecks accepted, unremoved membership in its database transaction. Responses use `Cache-Control: no-store`. Read state and preferences are independent between members. In-app opt-out hides the feed without deleting its shared alert events or changing webhook subscriptions. Re-enabling shows the existing selected history. Preferences do not suppress the operational alert engine. Cursors keep PostgreSQL microsecond precision even when the display timestamp has millisecond precision; new events appear when refreshing the first page. No count is fabricated for notifications outside the loaded page.

Email defaults off. `emailAvailable` requires configured delivery and this member's current verified recipient. `recipientVerified` reports whether the recorded recipient matches the member's issuer/subject; `emailRecipient` is that private verified address or `null`. `email` additionally requires explicit consent bound to that recipient revision. The signed OIDC sign-in path records or clears verified email for the freshly authenticated identity's currently accepted memberships; an address is never inferred from a subject, invitation or request body. Changing the recipient resets consent. `email:true` returns `409 email_unavailable` unless delivery is configured and the current recipient is verified; `email:false` disables future work and cancels pending delivery bookkeeping.

Optional email consumes the same immutable alert events through a durable per-member delivery outbox. Only selected events at or after explicit opt-in are eligible: enabling email never replays historical alerts or reroutes an old event to a new address. The worker rechecks membership, consent and recipient revision before sending. A request already started can still arrive after opt-out. Notices contain only a minimal operational template and an authenticated app link, without prompt/media/token content. See the [operational email runbook](EMAIL-NOTIFICATIONS.md) for fixed relay configuration, stable delivery IDs, frozen transport identity, retries and conservative handling of unknown acceptance. A relay's 2xx response means acceptance, not inbox delivery; source fixtures do not qualify real mail.

Fixture checks use synthetic alert events and injected email transports in isolated databases; they make no external delivery requests. Native PostgreSQL qualification covers multi-connection membership, claim and deduplication behavior separately from real relay, inbox and hosted migration qualification.
