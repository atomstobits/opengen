# Execution dispatch capacity integration

C6 supplies focused transactional primitives in `packages/engine/src/dispatch-capacity.ts` and an **unnumbered, unapplied schema proposal** in `packages/engine/schema-proposals/execution.sql`. The integration owner owns migration allocation (currently reserved 017), engine hooks, API/MCP registration and combined qualification. This module is fixture-backed; it does not enable production limits by itself.

Configure one workspace pool and a private stable provider supply pool. Managed operator supply is shared across workspaces using a stable supply-account ID. BYOK pools include workspace and stable connection ID. Credential rotation must retain that identity. Never derive pool identities/limits from request JSON, credential values or credential versions. Hashed pool IDs remain private internal state and are not customer DTO fields. Deployment-specific quotas may use separate configured supply IDs only when evidence establishes separate upstream capacity.

`maxActive` limits submission-intent/accepted/unknown occupancy. `maxQueued` bounds queued backlog independently. Zero queued capacity deliberately pauses **new admissions**, including when active capacity is free, because every admission first persists its queued identity. Lowering a limit never evicts accepted jobs; new work waits until usage drops below it. Existing idempotency replay bypasses backlog charging.

Use caller-owned READ COMMITTED transactions, lock the owning workspace financial row first, then the workspace pool, provider pool, dispatch slot, and any job state updates. The module locks pools in that fixed order and counts durable slots under those locks. Do not wrap it in a transaction while already holding another workspace/provider pool. Pool-size-one is supported because primitives never acquire another connection. Never call a provider inside a database transaction.

At admission, after authorization/input preparation and revalidation, insert the job, call `enqueueDispatchInTransaction`, and reserve funds in **one** transaction. Backpressure is HTTP 429 `dispatch_backpressure`; rollback the whole new admission on failure. Existing job/idempotency replay returns its original slot without consuming quota. Do not create a new job identity to recover from a timed-out admission.

Before submission, complete asset/credential preparation outside locks. In a short authoritative transaction, revalidate the queued job/lease and call `beginDispatchInTransaction`; only `acquired` authorizes **one** outbound submission after commit. Persist the engine attempt/status and capacity intent in this same transaction. `blocked` leaves work queued and must not increment attempt count, reserve another slot, or loop on the same oldest blocked job. `already_started` never authorizes a submit: resume/reconcile the existing task. A process crash after intent conservatively retains occupancy even if no request actually reached the provider.

The local queue-start deadline is checked immediately before durable submission intent using the database clock, including while capacity is full. The deadline is exclusive: `deadline <= now` expires. Only a queued slot with no intent can expire. `expireQueuedDispatchInTransaction` returns true once; integrate the corresponding never-submitted terminal result and ledger release in that transaction with the existing once-only financial settlement guard. `beginDispatchInTransaction` returns `expired` for both new and prior expiry, so that return value alone cannot authorize another financial release. Persist the deadline as immutable request metadata and include it in idempotency hashing. Reject runtime or provider-queue deadline claims that an adapter cannot enforce; this local deadline does not establish provider cancellation or a refund.

A worker lease, financial hold and provider occupancy have separate lifetimes. Lease expiry during submit calls `markDispatchUnknownInTransaction` and the existing conservative unknown transition. It does **not** release occupancy or funds. `releaseDispatchInTransaction` requires trusted terminal, explicit rejection, or operator reconciliation evidence, returns true once, and changes capacity only. A provider terminal result may release occupancy while billing stays held. Read failure, client disconnect, runtime limit, cancellation request and delivery failure are never release evidence. Fallback can enqueue a new attempt only after its predecessor is released, under the same workspace transaction; unknown attempts cannot fall back.

Worker scheduling must first call `claimAcceptedWorkInTransaction`, and run the delivery owner's due-receipt pass, independent of generation capacity. Polling, late billing and delivery reuse the same upstream job and never enqueue/acquire a generation slot. Only if accepted/delivery work is not due should the worker inspect eligible queued submits, skipping/rescheduling blocked candidates so one full supply does not block other supplies. Sweep due queued deadlines (including pools at full capacity) before/back alongside admission/dispatch so stale queued slots do not consume backlog forever. Accepted claims use leases and `SKIP LOCKED`; the helper intentionally leaves generation status, money and attempt count unchanged.

Focused PGlite tests exercise the actual schema and SQL transitions with synthetic workspaces and no financial mutations/provider calls. Native PostgreSQL multi-session race tests are supplied separately for the integrator; single-backend PGlite is not evidence of replica concurrency. Final integration must also prove populated upgrade/rollback compatibility, admission rollback, pre-submit revalidation, worker crash boundaries, delivery priority, API backpressure and once-only financial release.

Upgrade enablement must account for preexisting submitting/running/submission-unknown jobs before new capacity-controlled dispatch is enabled. Nullable telemetry/deadlines need no invented backfill, but counting zero slots for legacy accepted jobs would understate provider occupancy. The integrator must map known frozen billing connections/operator supply to the same stable pools and conservatively retain ambiguous occupancy, or pause new submissions to affected supply until reconciliation. Accepted polling/delivery must keep running throughout. This draft intentionally does not invent missing supply identity or backfill terminal jobs as active.
